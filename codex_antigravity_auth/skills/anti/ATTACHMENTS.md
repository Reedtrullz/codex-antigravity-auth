# Explicit image attachments

`--image PATH` attaches a local PNG or JPEG to every generation stage of a
consult, panel, compare, review, plan, or expanded workflow. Repeat it for up to
four images. Each file is limited to 2 MiB and the total to 4 MiB. Images are
captured once before generation, using bounded regular-file reads and identity
checks. Symlinks in the selected file or any parent component are refused; use
the real directory path when a convenience path is a symlink. Policy containment
is checked before capture and does not authorize following aliases. File changes
after capture do not change a running request.

```sh
python scripts/anti.py consult --model YOUR_IMAGE_MODEL --no-pre-read \
  --prompt 'Describe the layout in the attached screenshot.' --image screenshot.png --json
python scripts/anti.py panel --mode ask --model YOUR_IMAGE_MODEL --judge YOUR_IMAGE_JUDGE \
  --prompt 'Assess this layout.' --image screenshot.png --json
```

Choose configured model IDs advertised by your gateway. The helper requires a
compatible live capability catalog declaring both image input and data-URL
support. It checks every selected reviewer, judge, summary model and enabled
fallback before panel fanout, and checks each actual call. An unsupported stage
fails; the helper never silently drops an image or substitutes a text-only lane.
Images accompany summaries and judges too, even when their text was generated by
an earlier model. Retries and workflow expansion reuse the same captured bytes.

The helper recognizes PNG/JPEG signatures; it does not decode, resize, normalize,
strip EXIF, or certify that a file is a valid image. The gateway receives exact
original bytes encoded as data URLs. Metadata embedded in those files is sent
unchanged. URLs, inline data arguments, audio, video and binary-to-text fallbacks
are refused. There is no implicit screenshot capture, URL fetch, cloud upload,
or media editor. Image-only tasks use `consult --no-pre-read` or `panel --mode ask`;
review and plan retain their normal code/source scope alongside attachments.

## Privacy, accounting and retention

An optional [data policy](DATA_POLICY.md) checks all attachment paths before any
image bytes are read. Its route and stage checks still apply to each submission.
Secret scanning covers assembled **text only**, not pixels or embedded image
metadata. Image-aware acknowledgement hashes bind the text hash and ordered
image hashes/MIME/sizes; a text-only acknowledgement cannot authorize an image
request, and changed images require a new acknowledgement when a text match is
present. Supplying a file is the explicit image selection; it is not a claim
that its pixels have been inspected for secrets.

JSON reports `metadata.media_coverage` separately from code `coverage` and
`scopeStatus`: image indices, SHA-256, MIME, byte counts, checked routes and
bounded attempt traces. `gateway_attempts` counts dispatch attempts, including
retries and fallback; it does not prove provider delivery, image acceptance,
visual attention or review quality. A failed request may have been submitted.
`provider_image_acceptance` remains `unverified`. Preview/dry-run reports say
`not_sent` and make no catalog or generation requests. Text estimates printed by
dry-run exclude unknown image token costs; serialized request bytes remain part
of [attempt admission](SPEND_CONTROL.md).

Attachment paths and data URLs are not put into run metadata. Never mode retains
only fixed media counts and limitations. Summary mode reserves bounded image
hash/MIME/size receipts outside its text-preview budget; full mode also retains
bounded attempt details. Saved result artifacts include media receipts alongside
code coverage. Model-produced text remains subject to the usual recording and
redaction policy; no visual redaction or OCR is performed. Images are held in
memory, not copied into the run directory. [Checkpoint recipes](CHUNK_RESUME.md)
bind image identities, so a changed attachment cannot reuse old chunk output;
resume requires selecting the same files/bytes again.

## Evaluation status and release gate

This implementation is experimental. Synthetic fixtures can establish exact-byte
forwarding, lane/fallback restrictions, privacy decisions and recording behavior.
They do not establish real-media correctness or visual quality. **Real-media
evaluation is still required before release acceptance:** use separately approved
non-sensitive screenshots and capable routes, inspect actual provider output,
compare text-only controls, record omissions and failures, and keep cost/privacy
bounds explicit. No live provider/image evaluation is claimed by this change.
